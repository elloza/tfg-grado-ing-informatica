# Purpose and objectives

This section defines what the TFG aims to achieve. The DIA v2 guide asks for functional and personal objectives, with one main objective and several achievable, reasonable and measurable subobjectives {cite:p}`dia_documentacion_tfg_v2`.

The **main objective** should express the central contribution: building a system, designing a method, evaluating a technique, developing a prototype, automating a process, comparing alternatives or generating applicable knowledge.

The **subobjectives** split that promise into verifiable results. They are often clearer when written with action verbs:

- Analyze the problem and its constraints.
- Design an architecture or solution model.
- Implement a working prototype.
- Evaluate the solution through metrics, tests or user validation.
- Document the process so that it is reproducible.

## Functional and personal objectives

Functional objectives describe what the work should produce. Personal objectives describe relevant learning by the author, but only when connected to the TFG. "Learning a technology" is not enough; it is better to state that a specific technology will be applied and evaluated to solve a defined need.

## Quality criteria

An objective is well written if the final report can answer:

- Has it been achieved?
- With what evidence?
- What limitation remains?
- Which technical decision helped achieve it?

Do not turn this section into a wish list. If a subobjective cannot be verified in the report, annexes, repository or tests, it probably needs rewriting.
