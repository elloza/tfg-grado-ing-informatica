# La memoria

La memoria es el documento que el tribunal debe poder leer de principio a fin para entender el TFG. No debe contener todos los detalles técnicos, pero sí debe contener todas las decisiones importantes.

## Introducción

Presenta el problema, el contexto, la motivación y la estructura del documento. Una buena introducción permite que el lector sepa qué se ha hecho, por qué importa y cómo se organiza la memoria.

## Objeto y objetivos

Define un objetivo principal y subobjetivos medibles. Evita objetivos vagos como "aprender una tecnología" si no se traducen en resultados verificables.

## Antecedentes y situación actual

Aquí se contextualiza el dominio. Si el TFG es una aplicación para salud, educación, empresa o investigación, explica el dominio lo justo para entender el problema. Si hay productos similares, compáralos con criterio.

## Métodos, herramientas y modelos

Explica la metodología de desarrollo y las herramientas relevantes. No hace falta explicar qué es Visual Studio Code si no afecta al proyecto; sí hace falta explicar por qué se eligió una arquitectura, una librería de IA o un framework.

## Requisitos, alcance y restricciones

El lector debe entender qué entra y qué no entra en el TFG. Las restricciones no son excusas: son condiciones de diseño.

## Solución propuesta

Describe el producto final con arquitectura, funcionalidades, capturas, diagramas y forma de prueba cuando proceda. Si hay despliegue, repositorio, demo o vídeo, enlázalo.

## Riesgos y gestión

Incluye riesgos técnicos, riesgos de aceptación, riesgos de integración o riesgos de datos cuando tengan sentido. La planificación debe conectar con el trabajo real, no ser un Gantt decorativo.

## Conclusiones

Responde explícitamente a los objetivos. Explica resultados, limitaciones, aprendizajes y trabajo futuro. Una conclusión seria no dice solo "se han cumplido los objetivos"; demuestra cuáles, cómo y con qué evidencias.
