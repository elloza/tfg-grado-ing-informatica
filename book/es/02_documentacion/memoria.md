# La memoria

La memoria es el documento que el tribunal debe poder leer de principio a fin para entender el TFG. No debe contener todos los detalles tecnicos, pero si debe contener todas las decisiones importantes.

## Introduccion

Presenta el problema, el contexto, la motivacion y la estructura del documento. Una buena introduccion permite que el lector sepa que se ha hecho, por que importa y como se organiza la memoria.

## Objeto y objetivos

Define un objetivo principal y subobjetivos medibles. Evita objetivos vagos como "aprender una tecnologia" si no se traducen en resultados verificables.

## Antecedentes y situacion actual

Aqui se contextualiza el dominio. Si el TFG es una aplicacion para salud, educacion, empresa o investigacion, explica el dominio lo justo para entender el problema. Si hay productos similares, comparalos con criterio.

## Metodos, herramientas y modelos

Explica la metodologia de desarrollo y las herramientas relevantes. No hace falta explicar que es Visual Studio Code si no afecta al proyecto; si hace falta explicar por que se eligio una arquitectura, una libreria de IA o un framework.

## Requisitos, alcance y restricciones

El lector debe entender que entra y que no entra en el TFG. Las restricciones no son excusas: son condiciones de diseno.

## Solucion propuesta

Describe el producto final con arquitectura, funcionalidades, capturas, diagramas y forma de prueba cuando proceda. Si hay despliegue, repositorio, demo o video, enlazalo.

## Riesgos y gestion

Incluye riesgos tecnicos, riesgos de aceptacion, riesgos de integracion o riesgos de datos cuando tengan sentido. La planificacion debe conectar con el trabajo real, no ser un Gantt decorativo.

## Conclusiones

Responde explicitamente a los objetivos. Explica resultados, limitaciones, aprendizajes y trabajo futuro. Una conclusion seria no dice solo "se han cumplido los objetivos"; demuestra cuales, como y con que evidencias.
